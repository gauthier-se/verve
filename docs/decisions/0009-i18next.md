# 0009. i18next for internationalization

- **Status:** Accepted
- **Date:** 2026-10-22

## Context

The SPA is translated from day one (English and French), community translations should be easy, language changes must apply without reloading the page, and missing or hardcoded strings must be caught in CI. The two candidates were Paraglide JS 2 (compiled messages) and i18next 26 with react-i18next 17.

## Decision

- Use i18next with react-i18next.
- Translation files use the i18next JSON format: `web/src/locales/<language>/<namespace>.json`, English as the reference language.
- Use `i18next-cli` for key extraction, TypeScript type generation, translation status and linting of hardcoded strings.
- CI runs `i18next-cli extract --ci` and `i18next-cli lint` as blocking checks, and `i18next-cli status` as a non-blocking report.

  Amendment (2026-10-26): the check runs `extract --ci --dry-run`, because `--ci` alone writes the updated translation files while failing. Types are generated by `extract --with-types` instead of a separate `i18next-cli types` run.

## Consequences

- Changing the language re-renders the UI instantly, without reload.
- Keys are type-checked through generated types, close to the safety of a compiled approach.
- The i18next JSON format, including plurals, is supported natively by translation platforms such as Weblate.
- The runtime is heavier than Paraglide's compiled output, which does not matter for a self-hosted app embedded in a binary.

## Alternatives considered

- **Paraglide JS**: compile-time safety and minimal bundle, but changing the locale reloads the page by default, and its no-reload mode does not re-render the UI. Its message format is less widely supported by translation platforms.
