# Architecture

This document describes how Verve is put together. Feature-level behavior lives in [features/](features/), and the reasoning behind the main choices lives in [decisions/](decisions/).

## Goals and constraints

- **Single binary**: one executable contains the API, the web app, the job worker and the CLI. The only state is the data directory.
- **Self-hosted first**: no external service is required to run Verve. Optional integrations (OIDC, SMTP, ntfy, map tiles) are opt-in or replaceable.
- **Privacy**: no telemetry, no update checks by default, health values never appear in logs, metrics or notifications unless the user opts in.
- **Small hardware**: must run comfortably on a Raspberry Pi 4. Targets: idle memory under 100 MB, streaming XML import under 300 MB peak memory.
- **Household scale**: a handful of users, tens of millions of samples per user over many years.

## Backend

|---|---|

| Release | goreleaser, GitHub Actions, Taskfile for local development |

### Storage interfaces

Domain code depends on repository interfaces declared in `internal/store`, never on SQLite directly. The SQLite implementation lives in `internal/store/sqlite`. A Postgres implementation is not planned but must remain possible without touching domain code. Rules:

- No SQLite-specific types or functions leak out of `internal/store/sqlite`. A depguard rule in `.golangci.yml` fails lint when `modernc.org/sqlite` or `internal/store/sqlite` is imported outside `internal/store/sqlite` and `internal/app`, which wires the implementation.
- `store.Store` gives access to the repositories and is the unit of work: `WithTx(ctx, fn)` runs `fn` with repositories bound to one transaction, never a `*sql.Tx`. The transaction commits when `fn` returns nil, and rolls back when `fn` returns an error (returned unchanged) or panics (the panic propagates). `fn` must only use the repositories it receives: a write through the store inside `fn` would wait for the writer that `fn` holds.
- Outside `WithTx`, the SQLite repositories read on the reader pool and run each write in its own transaction on the writer.
- Missing records are reported with `store.ErrNotFound` and conflicting writes with `store.ErrConflict`, checked with `errors.Is`.
- Queries are written in SQL in `internal/store/sqlite/queries` and compiled by sqlc into `internal/store/sqlite/sqlcgen` with `task generate`. CI fails when the generated code is out of date.
- The contract suites in `internal/store/storetest` (for example `RunInstanceSettings(t, newStore)`) specify the behavior of each repository. Every implementation runs them against a real, migrated database, so that a second implementation can be validated against the same tests.
- Time values cross the interface as `time.Time` in UTC. Each implementation chooses its own on-disk representation.
- Aggregation logic that needs heavy SQL stays inside the implementation behind intent-revealing methods (for example `RecomputeHourly(ctx, userID, typeID, from, to)`).

### Job worker

A single worker pool polls the `jobs` table. Jobs have a kind, a JSON payload, a status, an attempt counter, a `run_at` time and a lease (`locked_until`). Failed jobs are retried with exponential backoff, then marked failed and surfaced to admins. Kinds include `import.xml`, `import.hae`, `aggregate.recompute`, `workouts.records`, `energy.daily`, `plan.checkin`, `notify.deliver`, `backup.run`, `export.build`, `cleanup.uploads`, `cleanup.sessions`.

SQLite allows one writer at a time. The database runs in WAL mode with two connection pools: a single writer connection whose transactions start with `BEGIN IMMEDIATE`, so concurrent writers queue instead of failing with `SQLITE_BUSY`, and a read-only pool that long writes (imports) never block. Writers use short transactions (bounded batches) so that API requests are never blocked for long. A `busy_timeout` is set on every connection. On shutdown the database is closed after the HTTP server has stopped, and the WAL is checkpointed with `TRUNCATE`.

## Frontend

| Concern | Choice |
|---|---|
| Framework | React 19 SPA built with Vite 8 |
| Routing | TanStack Router 1.x, file-based routes through the Vite plugin, typed search params ([ADR 0002](decisions/0002-tanstack-router-without-start.md)) |
| Server state | TanStack Query 5 |
| Tables | TanStack Table 9 |
| Forms | TanStack Form 1 |
| Charts | TanStack Charts 1.x behind wrapper components ([ADR 0003](decisions/0003-tanstack-charts-behind-wrappers.md)) |
| API client | generated from the OpenAPI spec with Hey API (`@hey-api/openapi-ts`) and its TanStack Query plugin |
| UI | Tailwind CSS 4 and shadcn/ui |
| Dashboard grid | react-grid-layout |
| Internationalization | i18next with react-i18next, i18next-cli ([ADR 0009](decisions/0009-i18next.md)) |
| Tests | Vitest, Testing Library, MSW, Playwright |
| Maps | MapLibre GL, optional PMTiles |

Routing state that users may want to bookmark or share (metric, period, granularity, filters) lives in typed search params, not in component state.

The OpenAPI spec is produced by the binary itself (`verve openapi > web/openapi.json`) and the client is regenerated as part of the build. A change to a Go API type that breaks the frontend fails the frontend type check.

The generated client lives in `web/src/api/generated`, with one TanStack Query options function per operation (for example `getMetaOptions()` for `get-meta`). `web/src/api/client.ts` configures it: requests go to the origin of the app with `credentials: 'same-origin'`, every request other than GET carries the header `Verve-Csrf: 1`, and an error response that is not `application/problem+json`, such as the error page of a reverse proxy, is replaced by a problem with its status and the code `unexpected_response`. The generated client throws the body of an error response, so every error it throws for a response is a problem, and the status of a proxy error is not lost.

The root route renders the app shell. `ConnectionGate` (`web/src/components/status/`) queries `/api/v1/meta` with `metaQueryOptions()` from `web/src/api/meta.ts`, refetched on window focus and every 5 minutes, never retried by TanStack Query, and run even when the browser reports no network (`networkMode: "always"`), so that an offline device gets the unreachable screen instead of a paused query. `classifyApiError()` from `web/src/api/errors.ts` tells a server that cannot be reached (a network error, 502 or 504 from a reverse proxy, or a 503 that is not a Verve problem, as a proxy answers when its backend is down) from a server that is starting (503 with the code `starting`) and from any other error. In the first two cases the gate replaces the layout with a full-page screen and refetches every 5 seconds until the server answers. Other errors let the layout through. `useVersionWatch()` from `web/src/lib/version-watch.ts` remembers the version of the first answer, and once the server reports another one, turns the next client-side navigation into a full page load of its target, so that the frontend of the new version loads.

## Data flows

### Ingestion

```
source payload
  -> adapter (xmlexport | healthautoexport | native): parse in streaming mode into normalized records
  -> catalog: map type identifiers, convert units to canonical units, parse time with offset
  -> sources: find or create the source for this user
  -> block rules: drop matching records, count them
  -> dedupe: compute the natural key, upsert in batches
  -> dirty ranges: record (type, time range) per user, enqueue aggregate.recompute
  -> import report: received, inserted, updated, duplicates, blocked, invalid, unsupported
```

See [Ingestion pipeline](features/ingestion-pipeline.md).

### Reads

Charts read from precomputed aggregates whenever the requested granularity allows it (hour, day, week, month, year). Raw samples are read only for short ranges (a single day, a workout, a night of sleep). The API downsamples long raw series server-side so the frontend never receives more points than it can draw.

## Conceptual data model

Every user-owned row carries a `user_id`. All queries are scoped by user, and the storage layer exposes no method that reads health data across users.

## Cross-cutting rules

### Time

- Samples are stored in UTC with their original UTC offset, so a sample can be shown in the local time where it was recorded.
- SQLite stores timestamps as `INTEGER` Unix milliseconds in UTC.
- "Today", daily aggregates and weekly boundaries are computed in the user's timezone preference. Changing the timezone triggers a recompute of daily aggregates.
- Sleep is attributed to nights using a configurable window (default 18:00 to 18:00, attributed to the wake-up date).

### Units

Values are stored in canonical units and converted only for display.

| Dimension | Canonical unit |
|---|---|
| Mass | kg |
| Length, distance | m |
| Energy | kcal |
| Duration | s |
| Heart rate, respiratory rate | count/min |
| Heart rate variability | ms |
| Temperature | degC |
| Percentages (SpO2, body fat) | fraction (0 to 1) |
| Blood glucose | mg/dL |
| Blood pressure | mmHg |
| Speed | m/s |
| VO2max | mL/(kg.min) |

### Security baseline

- Strict security headers on every response, set by `internal/httpapi/security.go` after request logging and before the router:
  - `Content-Security-Policy`: same-origin resources only (`default-src`, `script-src`, `font-src`, `connect-src`, `manifest-src`, `base-uri`, `form-action` are `'self'`), `style-src 'self' 'unsafe-inline'` because UI libraries set inline styles for positioning, `img-src 'self' data: blob:`, `worker-src 'self' blob:`, `object-src 'none'` and `frame-ancestors 'none'`. Scripts never need inline code. The policy is built with `CSP.With`, which the maps feature uses to add the tile host only when configured. A handler that sets its own policy with `Header().Set` keeps it.
  - `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=(), usb=()`, `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Resource-Policy: same-origin`.
  - `Strict-Transport-Security: max-age=31536000` only when `VERVE_PUBLIC_URL` is HTTPS.
- Session cookies are `HttpOnly`, `Secure` when `VERVE_PUBLIC_URL` is HTTPS, `SameSite=Lax`, and use the `__Host-` prefix when possible.
- State-changing requests require a custom header and a matching `Origin` (CSRF protection).
- Secrets at rest (TOTP secrets, OIDC client secret, SMTP password, webhook secrets) are encrypted with a key from `VERVE_SECRET_KEY`, or generated once in the data directory.
- `X-Forwarded-*` headers are trusted only from `VERVE_TRUSTED_PROXIES`.
- Logs never contain health values, tokens, passwords or session ids. The only exception is the first-run setup token, printed at startup outside the `slog` handler while no user exists (see [Accounts and administration](features/accounts-and-administration.md) FR-1).
- Secrets (single-use link tokens, API tokens, session ids, passwords) never appear in the path or query string of a URL that Verve serves or generates: the path is written to Verve's request log, and the path and query string reach reverse proxy access logs and the `Referer` header. A link that carries a secret, such as a setup, invitation or password reset link, puts it in the URL fragment (`#...`), which browsers never send to a server. The SPA removes the fragment from the address bar with `history.replaceState` right after reading it, before sending any request, keeps the secret in memory only and sends it to the API in a request body. The OIDC callback is the only exception: it receives `code` and `state` in the query string, the default response mode of the Authorization Code flow, and the code is single-use and bound to PKCE. The reasons are in [ADR 0010](decisions/0010-secrets-in-url-fragments.md).

### Errors

API errors use RFC 9457 problem details with a stable machine-readable `code`. The frontend translates codes into localized messages. One code comes from the API client rather than the server: `unexpected_response`, for an error response that is not a problem, such as the error page of a reverse proxy (see [Frontend](#frontend)).

The errors raised by Huma, such as validation errors, have the same shape: `huma.NewError` is replaced once, when the API is built, by a constructor of `Problem`. Their `code` defaults from the status: 400 `bad_request`, 401 `unauthorized`, 403 `forbidden`, 404 `not_found`, 409 `conflict`, 422 `validation_failed`, 429 `rate_limited`, 503 `unavailable`, any other client error `bad_request` and any other server error `internal`. Validation errors list one entry per invalid field in `errors`, with `message`, `location` (for example `body.name` or `query.limit`) and `value`. Server errors never have `errors`: an operation that fails with an error that is not a problem answers 500 `internal` with the detail `unexpected error occurred`, because the message of an internal error may hold file paths or queries.

## Testing strategy (proposed)

- Unit tests for pure computations: unit conversion, source selection, sleep assembly, zones, splits, best efforts, energy estimation, plan targets.
- Integration tests against a real SQLite database for repositories and the ingestion pipeline.
- Anonymized fixture exports (small `export.zip` and Health Auto Export payloads, version 1 and 2) checked into the repository.
- API contract: the generated OpenAPI spec is committed and diffed in CI.
- Smoke tests with Playwright against the production binary, in Chromium and WebKit, on every pull request.
- End-to-end tests for critical flows (setup, import, Today page) once M2 is reached.
